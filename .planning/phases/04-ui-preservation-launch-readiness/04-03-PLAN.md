  <name>Task 1: Deploy WS server to Railway and configure env vars</name>
  <files>none</files>
  <action>
This task requires human action because Railway and Vercel dashboard operations need authenticated access that Claude cannot perform.

**Step 1: Verify or deploy WS server on Railway**

Check if the ws-server is already deployed on Railway:
- Go to https://railway.com/dashboard
- Look for a service linked to this repo's `ws-server/` directory
- If deployed: note the public URL (should be something like `wss://ws-server-production-XXXX.up.railway.app`)
- If NOT deployed: create a new service from the `ws-server/` directory, Railway will auto-detect the Bun runtime via `railway.json`

**Step 2: Set env vars on Railway**

In the Railway service settings, set these environment variables:
- `DASHSCOPE_API_KEY` = (your DashScope API key from https://dashscope.console.aliyun.com/)
- `DASHSCOPE_VOICE_ID` = (the voice_id from Phase 1 enrollment, same value as in your local .env.local)
- `PORT` is set automatically by Railway — do not override

**Step 3: Set env vars on Vercel**

Go to https://vercel.com/ -> your project -> Settings -> Environment Variables:
- Set `NEXT_PUBLIC_WS_SERVER_URL` = `wss://[your-railway-url]` (use the URL from Step 1, with `wss://` protocol, NOT `ws://`)
- This var is inlined at build time, so you MUST trigger a redeploy after setting it

**Step 4: Decide branch deployment**

Decide whether to:
- (A) Merge `feat/openai-realtime` to `main` and deploy from main
- (B) Deploy the `feat/openai-realtime` branch directly (Vercel supports branch deploys)

If merging to main: `git checkout main && git merge feat/openai-realtime && git push origin main`
If branch deploy: configure Vercel to deploy from `feat/openai-realtime` or use the branch preview URL

**Step 5: Trigger production build**

After env vars are set, trigger a new Vercel deployment so `NEXT_PUBLIC_WS_SERVER_URL` is baked into the build.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser -> Railway WS | WebSocket crosses from user browser to Railway server; must use wss:// (TLS) |
| Railway -> DashScope | Server-side API calls with DASHSCOPE_API_KEY; key never exposed to browser |
| Vercel build -> env vars | NEXT_PUBLIC_WS_SERVER_URL baked at build time; only contains the public WS URL (not a secret) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-04 | Information Disclosure | DASHSCOPE_API_KEY | mitigate | Key is set only on Railway env vars (server-side), never in NEXT_PUBLIC_* or browser bundles |
| T-04-05 | Tampering | Mixed content (ws:// on HTTPS) | mitigate | NEXT_PUBLIC_WS_SERVER_URL must use wss:// protocol; task instructions explicitly warn against ws:// |
| T-04-06 | Denial of Service | Railway WS server | accept | Single-instance Railway deployment; acceptable for portfolio traffic levels |
</threat_model>
